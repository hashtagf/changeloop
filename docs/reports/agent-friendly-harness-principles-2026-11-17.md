# หลักการทำ harness ให้ agent พัฒนาโค้ดได้อย่างน่าไว้ใจ

**สถานะ:** บันทึกหลักการและสิ่งที่ทำแล้ว ณ 2026-11-17 (merge แล้วใน PR #4, #5, #11 และ #12;
ยังไม่ได้ออก release) **ผู้อ่าน:** maintainer และ agent ที่แก้โค้ด harness ของ
Change Loop เอง เอกสารนี้ไม่ใช่สัญญาของ runtime: กฎที่บังคับจริงอยู่ในตัวตรวจที่อ้างถึง
ด้านล่าง

ที่มา: ทอล์ก *All Code Is Slop (Except Mine)* ของ Lauren Tan (@poteto) และภาพ
"the poteto pyramid"

## หลักใหญ่

ความไว้ใจ agent ต้องมาจากสิ่งที่ระบบบังคับและตรวจได้ ไม่ใช่จากคำสั่งที่หวังให้ agent
อ่านแล้วทำตาม บทบาทของคนจึงเปลี่ยนจากคนที่คอยตามตรวจโค้ดทุกชิ้น เป็นคนออกแบบเงื่อนไข
ที่ทำให้โค้ดใหม่มีคุณภาพสม่ำเสมอ

## The poteto pyramid

ลงแรงจากชั้นบน (ต้นทุนต่ำ ได้ผลมาก) ลงล่าง (ต้นทุนสูง):

| ชั้น | ตัวอย่าง | ใน repo นี้ |
|---|---|---|
| codebase | API ที่ใช้ผิดยาก, สถาปัตยกรรม, refactor | กลุ่มใน `runtime/workflow/`, ไฟล์เล็ก, helper กลาง |
| static analysis | lint, type, test, CI | `scripts/lint/`, lint ratchet, architecture suite, repository hygiene |
| verification | runtime, formal | เทสต์หลาย process, mutation ที่ต้องถูกจับ |
| prose | rules, skills, `AGENTS.md` | เก็บเฉพาะเรื่องที่ต้องใช้วิจารณญาณ |
| human review | รีวิวของคน | รีวิวความหมาย หลังชั้นบนกรองแล้ว |

## หลักการ

1. **ลงแรงตามลำดับ pyramid** แก้ที่โครงสร้างโค้ดและตัวตรวจก่อน เพิ่มคำเตือนในเอกสาร
   เป็นทางสุดท้าย
2. **โค้ดคือตัวอย่างที่ agent จะลอกตาม** เก็บวิธีแก้ขัดที่ค้างอยู่ออก ไม่ใช่แค่ห้ามเพิ่ม
3. **ทำให้ทางที่ถูกง่าย และทางที่ผิดใช้ไม่ได้** เรื่องอันตรายทำได้ที่จุดเดียว:
   `runtime/core/timing.mjs` สำหรับการรอและ timer และ `runtime/core/best-effort.mjs`
   สำหรับจุดที่ตั้งใจไม่สนใจ error ที่อื่น lint ไม่ยอม และข้อความ error บอกว่าให้ใช้อะไรแทน
4. **โครงสร้างต้องสื่อความหมายและถูกบังคับจริง** ชื่อโฟลเดอร์บอกว่าโค้ดควรอยู่ที่ไหน
   ตัวตรวจทำให้กฎนั้นมีผล import จากไฟล์ที่เป็นเจ้าของโค้ด ไม่ผ่าน re-export
5. **Ratchet: ถอยหลังไม่ได้** ปัญหาเก่าเป็น baseline ได้แต่ห้ามเพิ่ม เก็บกวาดแล้วรัน
   `node scripts/lint/ratchet.mjs --tighten` ทันที การเพิ่ม baseline ต้องแก้ JSON
   ให้คนรีวิวเห็น
6. **ทุกครั้งที่ต้องแก้ agent ให้แก้ที่ระบบ** ความผิดพลาดที่เกิดซ้ำต้องกลายเป็นเทสต์,
   lint rule หรือการเปลี่ยน API (กติกานี้อยู่ใน `CLAUDE.md` ข้อ 5 ของ maintainer workflow)
7. **ตรวจลึกกว่า happy path** ใช้เทสต์หลาย process แข่งกันจริงพร้อม seed ที่ทำซ้ำได้
   และลองทำโค้ดให้พังเพื่อพิสูจน์ว่าเทสต์จับได้จริง
8. **เปลี่ยนแค่โครงสร้าง พฤติกรรมต้องเหมือนเดิม** ล็อกรายชื่อ export ไว้ก่อนย้ายโค้ด
   รันเทสต์ทุกขั้น ไม่แก้ค่าที่เทสต์คาดไว้เพื่อให้ผ่าน และทำทีละขั้นที่ย้อนกลับได้
9. **แก้ที่ต้นเหตุ ไม่ใช่อาการ** จำลองปัญหาให้เกิดซ้ำก่อนแก้ ไม่ใส่ retry หรือเพิ่ม
   timeout แทนการหาสาเหตุ
10. **ทำวงจรภายในให้แน่นก่อนขยาย** วงจรเขียนและตรวจโค้ดต้องน่าเชื่อถือก่อนเพิ่มจำนวน
    agent หรือระบบอัตโนมัติ ไม่เช่นนั้นระบบอัตโนมัติจะขยายปัญหาตามไปด้วย
11. **เลือกตามผลระยะยาว และรู้ว่าเมื่อไรควรหยุด** ไม่ฝืนเปลี่ยนที่ทำให้โค้ดอ่านยากขึ้น
12. **วัดก่อนแก้ และวัดซ้ำหลังแก้** แยกเวลาจาก log ของ host ว่าไปอยู่ที่โมเดล, harness
    หรือเทสต์ แล้วยืนยันด้วย paid run บน lane เดิม บอกจำนวนรอบที่รันเสมอ
13. **บอกกติกาก่อนให้ agent เขียน ดีกว่าส่งกลับให้แก้** ข้อความใน template สร้างจาก
    ค่าคงที่เดียวกับตัวตรวจ และมีเทสต์ยืนยันว่าตรงกัน
14. **field ที่บังคับต้องตอบตามจริงได้เสมอ** `none: <เหตุผล>` หรือ `unknown: <เหตุผล>`
    นับว่าตอบแล้ว ไม่บังคับให้แต่งข้อมูลขึ้นมา
15. **ข้อความ repair ต้องแก้ได้ในรอบเดียว** บอกเหตุผลที่ระบบประเมิน และให้ตัวอย่างที่
    copy ไปใช้ได้ทันที
16. **เทสต์ที่พังเพราะเครื่องช้าคือบั๊ก** แก้ช่วงเวลาหรือจุดเชื่อมของเทสต์ ไม่กด rerun

## วัดคุณภาพโค้ดและคุณภาพของ pyramid

`npm run quality:scorecard` (`scripts/quality/scorecard.mjs`) สรุปตัวเลขจาก baseline
ที่ commit ไว้ บน build ที่ผ่าน ratchet ค่า baseline เท่ากับโค้ดจริง CI พิมพ์ตารางลง job summary
และเก็บ JSON เป็น artifact ของแต่ละ commit (90 วัน) เพื่อดูแนวโน้ม

- **คุณภาพโค้ด:** lint, type, ไฟล์เกินเพดาน, ไฟล์ที่ซ้อนเกิน 5 ชั้น, block ที่ copy ซ้ำ
  ตัวตรวจการซ้อนและโค้ดซ้ำเป็นตัวเดียวกับที่ส่งให้โปรเจกต์ผู้ใช้ และอยู่ใน lint ratchet ของ repo แล้ว
- **คุณภาพของ pyramid:** กฎแต่ละข้อใน `CLAUDE.md` และ `AGENTS.md` มีแถวใน
  `quality/rule-enforcement.json` บอกชั้นที่บังคับ (architecture, type, lint, test, mutation),
  เหตุผลถ้าเป็น judgment หรือ prose ถ้ายังเป็นแค่เอกสาร ตัวชี้วัดหลักคือสัดส่วนกฎที่ตรวจได้ซึ่งมี
  ตัวตรวจจริง และ `--check` ไม่ให้กฎที่เป็นแค่เอกสารเพิ่ม (`proseOnlyCeiling`) และจับ quote ที่
  ไม่ตรงกับเอกสารแล้ว

ค่าแรก ณ วันที่บันทึก: lint 0, type 251, ไฟล์เกิน 1,000 บรรทัด 10, ไฟล์ซ้อนเกิน 5 ชั้น 39

## สิ่งที่ตัดสินใจไม่ทำ และเหตุผล

- **แยก `foundation.mjs`:** ยังมี 6 จุดที่ runtime พึ่งกันเป็นวงจริง เรียงใหม่แล้วยังเหลือ
  58 statement ในวงเดียว แต่ละชิ้นที่แยกต้องรับ dependency 60–135 ตัว ต้องกลับทิศ
  dependency ระหว่าง runtime ก่อน
- **เทสต์ฆ่า process ตรง checkpoint ของ Land:** ต้องเพิ่ม hook ทดสอบในโค้ดที่ส่งให้ผู้ใช้
  และมีเทสต์จำลองการสะดุดครบทั้ง 14 checkpoint กับเทสต์ e2e ที่ตรวจว่า HEAD และ index
  ไม่เปลี่ยนอยู่แล้ว
- **ตัด `workTypeExamples` ออกจาก template:** spec `readable-change-packets` กำหนดให้
  มีตัวอย่างทุกชนิดงาน และการขอแยกทีละชนิดเพิ่ม request มากกว่าที่ประหยัด
- **แบนคอมเมนต์เกือบทั้งหมดแบบในทอล์ก:** คอมเมนต์ที่อธิบายเหตุผลยังมีประโยชน์ จัดการ
  เฉพาะคอมเมนต์ที่อธิบายวิธีแก้ขัด

## งานระยะยาวที่เหลือ

1. กลับทิศ dependency เพื่อตัดวงระหว่าง runtime แล้วจึงแยก `foundation.mjs`
2. type error เหลือ 0 แล้ว (PR ถัดจาก #16); ขั้นต่อไปคือเปิด `strict` ทีละโดเมน
3. ลดไฟล์ที่ยังเกิน 1,000 บรรทัดให้ต่ำกว่าเพดาน แล้วลดเพดานเป็น 800
4. ลดไฟล์ที่ซ้อนเกิน 5 ชั้น (39 ไฟล์ ลึกสุด 7) ส่วนใหญ่เป็น object literal ใน factory
5. (เสร็จแล้ว) ทุกไฟล์เทสต์มี row ใน `.claude/tests/README.md`; baseline ว่างและต้องว่างต่อไป
6. เพิ่มเทสต์ `advance` ของ change เดียวกันที่รันพร้อมกันหลาย process

## เช็กลิสต์ก่อนแก้โค้ด harness

- โค้ดใหม่อยู่ในโดเมนและกลุ่มที่ถูกต้องหรือไม่ และ import ทิศทางถูกหรือไม่
- ต้องรอหรือไม่สนใจ error ใช่ไหม ถ้าใช่ ใช้ `timing.mjs` หรือ `best-effort.mjs`
- import จากไฟล์ที่เป็นเจ้าของโค้ดหรือไม่
- ไฟล์จะเกิน 1,000 บรรทัดหรือไม่ ถ้าใช่ แยกโมดูลก่อน
- agent เคยทำผิดแบบนี้แล้วหรือไม่ ถ้าใช่ เพิ่มเทสต์หรือ lint rule ไม่ใช่คำเตือน
- ข้อความที่อธิบายกฎสร้างจากค่าคงที่ของตัวตรวจหรือไม่ และ repair บอกวิธีแก้ที่ copy ได้หรือไม่
- เปลี่ยน output ของคำสั่ง CLI หรือไม่ ถ้าใช่ รัน `.claude/tests/harness/run-installer-tests.sh` ด้วย
- จบงานแล้วรัน `--tighten` และเทสต์ชุดปกติ (`bash .claude/tests/run-all.sh`)
